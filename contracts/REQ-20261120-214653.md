# 权限点管理筛选功能

## 背景
- 现状：权限点管理页（`PermissionsPage.tsx:124` 显式 `searchable={false}`）无任何筛选 UI；前端 `systemApi.permissionList(page, size, signal)`（`packages/core/src/api/system.ts:386`）连 keyword 都不透传；后端 `PermissionController.list()`（GET /admin/v1/system/permissions）**已支持 `keyword`**（code/name 模糊，`PermissionUseCase.page:72-81`），但不支持 status/httpMethod；msw 权限点列表 handler（`mocks/handlers/system.ts:565`）只分页不过滤。
- 可复用资产：`CrudTable` 内建 `filters` prop＋FilterField；`useCrud` 的 `search/setFilter/resetFilters`（空值不进查询串）；筛选交互参照实现=UsersPage（搜索框＋下拉筛选）。
- 影响面红线（签名必须向后兼容）：`systemApi.permissionList` 另被 `RolesPage.tsx:190` 以 `permissionList(1, 500)` 无筛选调用；后端 `PermissionUseCase.page()` 生产调用方仅 `PermissionController.list()`，另有既有集成测试 2 处直接调用（`SystemIntegrationTest.java:258,260`）。
- 字段事实：`PermissionType` 枚举仅 API 一个值（类型筛选无区分度，不加）；`httpMethod`/`httpPath` 可空（null=非接口型）；`status` 用 `EnableStatus`（ENABLED|DISABLED）。
- mock 权限点样例（`mocks/data.ts:129-132`）现仅 2 条且全 ENABLED——需补 DISABLED 样例，否则状态筛选无可演示命中。
- 非法枚举参数：框架 `GlobalExceptionTranslator` 既有口径=MethodArgumentTypeMismatchException→HTTP 400＋Result 信封（WebError.BAD_REQUEST），直接沿用，不新增错误码。
- 表格现状无状态列（columns 仅 code/name/type/http/actions）——见 AC-15 待确认项。

## API
### 权限点分页查询（GET /admin/v1/system/permissions）——既有接口新增可选 query 参数
- 新增可选参数（全部可选；提供多个时 AND 语义）：
  - `keyword`：字符串；**既有参数**，沿用现状语义（permissionCode/permissionName 模糊匹配），本次不改其匹配范围
  - `status`：ENABLED|DISABLED，精确匹配（新增）
  - `httpMethod`：GET|POST|PUT|PATCH|DELETE，精确匹配（新增；`http_method` 为 null 的记录不命中任何 httpMethod 筛选）
- 不携带参数 → 行为与现状完全一致（keyword 原有语义不动）
- 返回：`PageResult<AdminPermissionView>`（DTO、分页形状、排序 permissionCode asc 均不变）；权限沿用 PERMISSION_LIST
- 服务层集成点（TL 收口，防并行漂移）：`PermissionUseCase.page` 签名扩展为 `page(PageQuery query, String keyword, EnableStatus status, String httpMethod)`（null=不过滤）；既有 2 处测试调用补 null 实参（编译兼容修正，非语义变更）；status 用 `EnableStatus` 枚举绑定，httpMethod 动词白名单校验，非法值均→HTTP 400＋Result 信封 WebError.BAD_REQUEST（框架既有翻译器行为）
- 失败：非法枚举值/非法动词→HTTP 400；成功分页 code 按 PageResult 现状
- 不新增错误码；POST/PUT/DELETE/GET /{id} 等其余接口不动

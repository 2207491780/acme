# AI 开发默认走工作树（取代「用户要求并行才启用」的口径）

日期：2026-11-13
取代：`2026-11-13-03-parallel-dev-mirror-gate.md` 中「触发条件 = 用户要求并行开发 / 多任务」的限定。

## 背景

03 把工作树定位为并行开发手段，触发条件写成「用户要求并行开发 / 多任务同时推进」。实践（2026-11-13）
显示：单会话任务仍直接在主工作树执行——占住 HEAD、临时切分支、长测试与派生文件互写风险依旧存在；
而「什么时候算并行」由 AI 自行判断，等于没有默认纪律。用户决定：所有开发都按工作树来，
不再依赖提示词激活。

## 决定

1. **默认适用**：凡会产生提交的开发（功能 / 修复 / 配置 / 文档）一律先 `node .ai/worktree.mjs add`，
   单会话也不例外。
2. **主工作树收敛用途**：只承载合并、推送与只读分析；只读分析不需要工作树。
3. **规则只留触发句**：`git-workflow.md`「分支模型」写明默认适用与入口命令，流程细节留在
   `parallel-dev.md`（受 `rulesBudgetBytes` 约束）。
4. **口径同步**：手册标题与触发描述、`PLAYBOOK-GUIDE`、`ARCHITECTURE`、`worktree.mjs` 注释统一改为
   「开发工作树」，不再暗示「并行才用」。

## 被否的选项

- **保持「用户要求并行才启用」**：否决——判断权在 AI，实际等同可跳过；本次违规正是该缺口。
- **只改手册、不改规则**：否决——手册不进入会话上下文，规则才是所有工具的必读入口。
- **用钩子强制「非工作树就拒绝提交」**：否决——主工作树上的合并提交与热修会被一并拦截，需要白名单；
  判定成本高于收益，且 CI 没有工作树概念。规则 + 流程保障即可。
- **在 CI 里限制提交来源**：否决——CI 只看到推送结果，无法识别本地工作树。

## 3. 术语和定义

3.1 **限界上下文**（Bounded Context）：业务能力的边界。同一术语在不同上下文可有不同含义，服务按限界上下文划分。

3.2 **能力域**：一组内聚业务能力的统称，是服务命名与拆分的依据。

3.3 **平台服务**（`platform-**`）：提供平台级业务能力（如用户、认证、消息）的服务。

3.4 **业务服务**（`business-**`）：承载单一业务域完整闭环的服务。

3.5 **契约模块**（`*-api`）：服务对外暴露的 DTO、枚举与调用接口集合，是服务间唯一的编译期依赖入口。

3.6 **BFF**（Backend For Frontend）：为特定端做聚合与裁剪的适配层服务。

3.7 **幂等**：同一请求执行一次与多次产生的结果一致。

3.8 **最终一致**：不保证多个操作同时成功，允许短暂不一致，最终达到一致状态。

3.9 **读模型**：为查询效率而冗余构建的本地数据副本，由事件或接口同步。

3.10 **灰度发布**：先向部分流量开放新版本、观察后再全量的发布方式。

3.11 **traceId**：贯穿一次用户请求全链路的追踪标识。

3.12 **死信**：多次消费失败后转入的隔离消息，用于人工或定时补偿处理。

3.13 **服务令牌**：服务间调用时用于证明调用方身份的内部凭证。

3.14 **多租户**：单套系统承载多个租户数据、通过隔离机制保障数据归属的架构形态。

## 4. 总体架构

### 4.1 拓扑

```text
B 端客户端            C 端客户端（App / 小程序 / H5）
     │                        │
     └────────┬───────────────┘
              ▼
     ┌──────────────────┐
     │  acme-gateway    │  统一入口：路由、验签、限流、灰度、日志
     └────────┬─────────┘
              │
   ┌──────────┴───────────┬──────────────────┐
   ▼                      ▼                  ▼
platform-**  (N 个)   business-**  (N 个)   外部依赖
   │                      │
   └──────────┬───────────┘
              │  同步：OpenFeign（仅经 *-api）；异步：MQ
              ▼
     注册/配置 Nacos · 缓存 Redis · 消息 RocketMQ · 链路 OTel/SkyWalking
```

### 4.2 分层与职责

| 编号 | 层 | 载体 | 定位 | 变更频率 | 数量趋势 | 规范章节 |
|---|---|---|---|---|---|---|
| ① | parent | `acme-parent` | 构建规范唯一来源 | 极低 | 固定 1 | 6 |
| ② | common | `common-*` | 语言层补充与共享契约基元 | 极低 | 固定，少量 | 7 |
| ③ | framework | `framework-*` | 分布式技术能力适配 | 低 | 按需扩展 | 8 |
| ④ | 网关 | `acme-gateway` | 双端统一接入 | 低 | 固定 1 | 11 |
| ⑤ | 平台服务 | `platform-**` | 平台级业务能力，可独立部署 | 中 | 只减不增（新增须架构评审，见 4.3.7） | 4.3、5 |
| ⑥ | 业务服务 | `business-**` | 业务域，可独立部署 | 高 | 持续新增 | 4.3、5 |

### 4.3 服务边界划分原则

4.3.1 服务应按限界上下文（3.1）划分，一个服务对应一个业务能力；数据独占要求见 12.1.1。

4.3.2 满足以下任一条件时，宜考虑拆分为独立服务：

- 需要独立伸缩（读写比例或峰值差异显著）；
- 需要独立发布节奏（变更频率与其余模块差异 ≥ 3 倍）；
- 归属不同团队且协作成本高于调用成本；
- 事务边界清晰，无强一致跨域需求。

4.3.3 不得按技术分层拆分服务（如 user-controller-service、user-dao-service）。

4.3.4 不得拆分出仅包装单表的服务；一个服务应至少包含一个完整的业务动作闭环。

4.3.5 初期服务总数宜控制在 5–8 个，随业务复杂度增长再拆，不得一次性铺设完整服务矩阵（M-15）。

4.3.6 平台服务与业务服务的具体数量不设固定配额，按能力域与拆分信号动态确定；服务数量变化不应引起 `common-*`、`framework-*` 的调整（规则见 7.2.3）。

4.3.7 新增 `platform-**` 应经架构评审，宜优先在既有平台服务内扩展能力；平台服务数量宜随能力整合逐步收敛。

### 4.4 依赖方向

4.4.1 依赖关系应单向：`business-** → platform-**（仅经 *-api） → framework-* → common-* → parent`。

4.4.2 服务之间仅可通过 `*-api` 模块建立编译期依赖，不得依赖其他服务的实现模块（M-02），以保证服务自治与独立部署。

4.4.3 `platform-**` 不得依赖任何 `business-**`。

4.4.4 `common-*` 与 `framework-*` 不得依赖任何服务模块。

4.4.5 服务的编译期依赖与运行期调用均不得成环（M-06）；出现环即视为服务边界划分错误，应重新划分边界或改为异步。

## 5. 工程结构

### 5.1 仓库结构

`acme-parent` 与 `acme-cloud` 为**平级**目录；`acme-cloud` 是下分子聚合，`acme-parent` 只提供继承，不做聚合。

```text
acme/                                  # 仓库根，不含 pom
│
├── acme-parent/                       # ① 父 POM，packaging=pom，无 <modules>
│
└── acme-cloud/                        # 总聚合器（下分子聚合）
    ├── acme-common/                   # ② 公共：common-*
    ├── acme-framework/                # ③ 框架：framework-*
    ├── acme-gateway/                  # ④ 网关
    ├── acme-platform/                 # ⑤ 平台服务：platform-**/
    └── acme-business/                 # ⑥ 业务服务：business-**/
```

5.1.1 每个服务目录下仅要求契约模块与实现模块两类（`*-api`、`*-service`）；领域模型复杂时可增设 `*-domain`。更细的内部目录由各服务自行决定，本文不作规定。

### 5.2 模块类型与职责

5.2.1 构建模块（`acme-parent`、`acme-cloud`）的职责分界见 6.1；代码模块按下表执行。

| 模块类型 | 职责 | 允许依赖 | 禁止（条款） |
|---|---|---|---|
| `common-*` | 跨服务共享的契约基元与工具 | SLF4J、Jackson 等基础三方库 | 见 7.1.3 |
| `framework-*` | 分布式能力封装，starter 化、可插拔 | `common-*`、中间件客户端 | 业务规则（8.1.2）、依赖服务模块（4.4.4） |
| `acme-gateway` | 路由、验签、限流、灰度、访问日志 | `common-*`、鉴权相关 framework | 业务逻辑与直连数据库（11.1.2） |
| `*-api` | DTO、枚举、服务调用接口 | `common-*`、`platform-**-api`、`spring-cloud-openfeign-core`（仅调用契约声明） | 实现类与 Web/ORM 依赖（9.1.2） |
| `*-service` | 服务的实现与启动入口 | 本服务 `*-api`/`*-domain`、其他服务 `*-api`、framework | 其他服务的 `*-service`（4.4.2） |
| `*-domain`（可选） | 领域模型与领域规则 | 仅纯 Java | Web 框架、ORM 具体实现 |

### 5.3 部署单元清单（按类型）

| 部署单元类型 | 模块 | 职责 | 伸缩依据 |
|---|---|---|---|
| 网关 | `acme-gateway` | 统一入口、鉴权、限流、灰度 | QPS |
| 平台服务（N 个） | `platform-**-service` | 平台级业务能力 | 按能力域独立指标 |
| 业务服务（N 个） | `business-**-service` | 各业务域的业务闭环 | 按域独立指标 |
| BFF（可选） | `portal-bff` / `admin-bff` | C 端聚合与裁剪 | 聚合接口 QPS |

5.3.1 平台服务与业务服务的具体数量、名称在各服务拆分评审通过后登记，不在本文固化。

5.3.2 新增或合并服务时，仅变更对应子聚合器（`acme-platform` / `acme-business`）的模块清单、`acme-cloud` 的 `dependencyManagement` 登记（见 18.1.1 第 3 步）与网关注册，不得改动 common、framework 的结构。

5.3.3 服务清单应以清单文件形式与代码同仓维护，作为部署与容量规划的唯一依据。

### 5.4 命名约定

| 写法 | 含义 |
|---|---|
| `platform-**` | 任一平台服务 |
| `business-**` | 任一业务服务 |
| `platform-**-api` / `platform-**-service` | 对应服务的契约模块与实现模块 |
| `com.acme.platform.<域>` / `com.acme.business.<域>` | 服务内包名 |

5.4.1 `**` 为占位通配，不代表字面星号，实际落地时替换为具体能力域名。

5.4.2 服务名应体现能力域而非组织形式，不得使用 `platform-module1`、`business-service2` 等编号式命名（M-16）。

5.4.3 服务的模块名、应用名（`spring.application.name`）与配置中心标识应使用同一名称（如 `platform-user`、`business-order`），避免多处不一致导致定位困难。

5.4.4 `platform-**` 的类名与包名不得出现具体业务域词汇；命名应体现平台能力域。

5.4.5 BFF 服务命名采用 `<端>-bff`（如 `admin-bff`、`portal-bff`），不归入 `platform-**` / `business-**`；其模块名、应用名与配置中心标识的一致性要求同 5.4.3。

## 6. 构建层级规范

### 6.1 POM 职责分界

| 维度 | acme-parent | acme-cloud |
|---|---|---|
| 定位 | 怎么构建 | 构建什么 |
| `<modules>` | 不得声明 | 仅声明子聚合 |
| 内容 | Java 版本、编码、版本 properties、三方件 `dependencyManagement`、`pluginManagement`、profiles、`distributionManagement` | `parent` 指向、`<modules>`、本项目模块 `dependencyManagement`、`spring-boot-maven-plugin` 启用、镜像构建配置 |
| 发布物 | 仅 pom | 聚合构建与汇总 |

### 6.2 parent 引用规范

6.2.1 `acme-cloud` 的 `<parent>` 应显式声明 `relativePath` 指向 `../acme-parent/pom.xml`。

6.2.2 `acme-cloud` 下的层聚合器（`acme-common` 等）与直管模块的 `<parent>` 指向 `acme-cloud`；层聚合器之下代码模块的 `<parent>` 指向所属层聚合器；`relativePath` 均使用默认值。

6.2.3 `acme-parent` 不得声明 `<modules>`（M-01），避免形成第二聚合器导致版本漂移；多产品线扩展时各产品线独立建立聚合器并统一继承 `acme-parent`。

### 6.3 版本管理

6.3.1 工程版本使用 `${revision}`，由 `flatten-maven-plugin` 在 install/deploy 时展开。

6.3.2 工程版本由 `acme-cloud` 重写 `${revision}` 统一决定，`acme-cloud` 及其全部子模块版本应一致；`acme-parent` 为共享基线、版本独立演进，`acme-cloud` 的 `<parent>` 应显式指向基线版本（见 6.2.1）。

6.3.3 三方依赖版本集中定义于 `acme-parent`；不得单独拆出被 parent `import` 的 BOM 模块（M-14）。

6.3.4 各服务可独立发版，但同一环境的服务集应遵循统一的兼容版本矩阵，矩阵记录于发布单。

6.3.5 发布版本不得包含 SNAPSHOT 依赖。

### 6.4 构建入口与增量构建

6.4.1 全量构建：`mvn -f acme-cloud/pom.xml clean install`。

6.4.2 CI 应支持按变更增量构建：使用 `mvn -pl <changed-modules> -am`，仅构建变更模块及其上游依赖。

6.4.3 冷启动时宜先执行 `mvn -N install -f acme-parent/pom.xml`。

6.4.4 不得在子模块目录内单独 install 作为交付手段。

## 7. common 规范

### 7.1 职责与依赖边界

7.1.1 职责：跨服务共享的最小契约基元——统一响应体、错误码、异常基类、分页对象、上下文持有者、trace 常量、服务调用所需的头部定义。

7.1.2 允许：纯逻辑封装、无状态、无 IO、无 Spring Bean 注解；编译期最多依赖 SLF4J、Jackson、jakarta.validation-api；Lombok 仅限编译期注解处理，测试栈（JUnit、AssertJ、Testcontainers 等）仅限测试域（common-test）。

7.1.3 禁止：

| 禁止项 | 说明 |
|---|---|
| `@Service` / `@Mapper` / `@RestController` | common 不依赖容器 |
| 数据库、缓存、HTTP 客户端 | 属于 framework |
| 业务实体 | 属于对应服务的 `*-api` |
| 需频繁变更的枚举 | 不得固化于 common；确需跨服务共享时放对应契约模块，并遵循 7.2.2 |

### 7.2 变更与兼容

7.2.1 common 的迭代必须向后兼容：只允许新增类与方法，不得修改已有方法签名或语义。

7.2.2 跨服务共享的枚举与常量应集中存放并保持稳定；单个枚举值的新增视为兼容，删除或重命名视为破坏性变更，需同步全部使用方。

7.2.3 common 的模块划分不得依据服务数量调整；服务增减不应引起 common 变更（另见 4.3.6）。

7.2.4 common 升级后应触发全量服务回归，不得仅验证单个服务。

## 8. framework 规范

### 8.1 职责与封装原则

8.1.1 职责：分布式场景下的技术能力封装。每个技术能力应独立封装为可插拔模块，具备「一行配置或一个注解即可开启／关闭」的特性，关闭后行为与未引入一致。

8.1.2 禁止在 framework 中编写业务规则；禁止以 `XxxService` 命名框架组件。

8.1.3 配置项前缀统一为 `acme.<module>`，所有配置项应提供默认值。

### 8.2 技术能力清单

8.2.1 framework 应覆盖以下技术能力：

| 能力 | 要求 | 禁止 |
|---|---|---|
| 认证与令牌解析 | 网关验签、下游令牌解析、内部服务令牌校验 | 硬编码角色与权限点 |
| 链路追踪 | traceId 生成与透传支持、日志 MDC 注入 | 业务日志格式化 |
| 幂等 | 基于 token 或业务键的幂等、结果缓存、并发互斥 | 业务幂等键的定义 |
| 限流与熔断 | 资源定义、默认规则、降级返回体 | 具体业务的兜底数据 |
| 分布式事务 | 事务分组配置、失败回滚策略 | 默认开启（应按需引入） |
| 任务调度 | 执行器注册、分片、失败重试 | 具体任务实现 |
| 数据访问增强 | 分页、多租户、逻辑删除、字段加解密 | 业务表结构 |
| 缓存与锁 | 缓存抽象、分布式锁 | 业务缓存键的定义 |
| 消息 | 生产与消费模板、死信处理 | 业务消息内容 |
| 导入导出 | 通用 Excel 读写 | 业务字段映射 |

## 9. 服务契约规范

### 9.1 契约模块边界

9.1.1 `*-api` 模块是服务间唯一的编译期依赖入口（见 4.4.2），仅含 DTO、枚举与服务调用接口。

9.1.2 `*-api` 不得包含实现类，不得依赖 Web 容器、ORM 或任何实现框架（M-11），契约与实现不得混同。允许依赖 `spring-cloud-openfeign-core` 以声明服务调用契约（仅注解与编解码契约，不含 Web 容器）。

9.1.3 `*-api` 的 artifact 名不含服务序号或环境标识，同一契约在全部环境使用同一坐标。

### 9.2 DTO 约定

9.2.1 DTO 应为不可变对象，字段使用包装类型，避免基本类型默认值歧义。

9.2.2 DTO 字段应显式表达可选性；可选字段缺省为 null 时，消费方应按 9.4.1 的假设约束处理。

### 9.3 版本与兼容性

9.3.1 接口版本通过 URL 前缀区分（`/v1`），破坏性变更应启用新版本并行一段时间。

9.3.2 变更兼容性规则：

| 变更类型 | 是否兼容 | 处理方式 |
|---|---|---|
| 新增可选字段 | 兼容 | 直接发布 |
| 新增枚举值 | 兼容 | 消费方需具备未知值兜底 |
| 字段改名 | 不兼容 | 新旧并存一个版本周期 |
| 删除字段 | 不兼容 | 先标记废弃，观察调用方后再删 |
| 修改字段类型 | 不兼容 | 新增字段替代 |
| 修改接口语义 | 不兼容 | 新版本接口 |

### 9.4 消费方约束与契约测试

9.4.1 消费方不得假设提供方的返回顺序、空集合与 null 等价、错误码全集。

9.4.2 契约文件应纳入版本管理；契约测试要求见 16.1。

## 10. 服务实现规范

### 10.1 内部分层职责

| 层 | 职责 | 约束 |
|---|---|---|
| 接口层 | 参数校验、视图对象转换、权限标注 | 不得含业务规则（事务约束见 10.2.1） |
| 应用层 | 用例编排、事务边界、跨服务编排 | 单方法对应单一用例 |
| 领域层 | 实体行为、状态机、领域校验 | 不依赖 Web、不得直接发起远程调用 |
| 基础设施层 | 持久化、远程调用、消息、缓存 | 不得含业务判断 |

10.1.1 上述分层为职责约束，不限定目录命名与文件组织方式。

### 10.2 事务

10.2.1 事务边界应位于应用层，且仅覆盖本服务数据库。

10.2.2 不得在事务内进行远程调用（M-05），避免长事务与故障传导；确需调用时应采用「本地事务 + 消息」模式。

10.2.3 跨服务一致性默认采用最终一致（3.8），方案优先级递减：本地消息表 → 事务消息 → Saga 编排 → 分布式事务框架。

10.2.4 使用强一致分布式事务需经架构评审，且仅限分支事务数量少、执行时间短的场景。

### 10.3 幂等与重试

10.3.1 所有写接口应支持幂等（3.7），幂等键由业务语义决定（单据号、请求 ID、外部流水号）。

10.3.2 消息消费必须幂等，使用消费记录表或去重键（M-12），防止重复消费导致数据错乱。

10.3.3 重试仅适用于幂等接口；重试策略应指数退避并设置上限，不得超过下游超时预算。

### 10.4 超时预算

10.4.1 全链路超时应满足：上游超时 > 下游超时 + 网络开销，逐层递减。

10.4.2 所有远程调用必须显式设置连接超时与读取超时，不得使用框架默认值。

### 10.5 异常与错误码

10.5.1 业务异常应继承 common 异常基类，携带错误码与面向调用方的提示信息；不得以异常作为业务分支的控制流。

10.5.2 错误码应全局唯一，采用「服务标识 + 模块段 + 序号」结构统一分配，分段规则由 common 定义；已废弃的错误码不得复用。

10.5.3 框架异常与三方依赖异常应在接口层统一转换为标准响应体，不得将原始异常信息直接返回调用方。

10.5.4 对外响应与日志不得暴露堆栈、SQL、内部地址等实现细节。

## 11. 网关与 B/C 双端规范

### 11.1 网关职责

11.1.1 网关负责：路由、令牌验签、身份头注入、限流、灰度分流、访问日志、跨域、响应体统一封装（仅限网关自身错误响应；业务响应由服务侧接口层按 10.5.3 封装，网关不得二次包装）。

11.1.2 网关不得承载业务逻辑、不得直连数据库、不得做数据聚合（M-09），防止网关成为瓶颈与变更热点；聚合需求应下沉为 BFF 服务（选型见 11.2）。

11.1.3 网关路由应按端划分前缀：B 端 `/admin/**`，C 端 `/app/**`；两套前缀应配置独立的鉴权与限流策略。

11.1.4 网关路由表应按服务能力域注册，新增服务时仅追加路由，不得改动既有路由。

### 11.2 双端形态选型

11.2.1 按下表选择双端形态：

| 方案 | 适用 | 代价 |
|---|---|---|
| 单服务双接口（推荐） | 绝大多数业务域 | 服务内需区分两端视图对象 |
| BFF 服务 | C 端存在跨服务聚合、裁剪的场景 | 多一层部署单元与调用链 |

11.2.2 默认采用单服务双接口；当 C 端单页面需聚合 ≥ 3 个服务的数据时，宜引入 `portal-bff`。

### 11.3 业务逻辑单点

11.3.1 业务逻辑应在应用层与领域层实现且仅实现一次。

11.3.2 不得为 C 端复制一份业务实现（M-08），避免维护成本翻倍与两端行为不一致；C 端差异仅允许体现于接口层的编排、视图对象裁剪与限流策略。

### 11.4 双端差异对照

| 维度 | B 端 `/admin` | C 端 `/app` |
|---|---|---|
| 认证 | 账号密码 + 多因子，短会话 | 验证码 / 三方登录，令牌 + 刷新 |
| 授权 | RBAC + 菜单 + 数据权限 | 资源归属校验（本人 / 家庭成员 / 企业成员） |
| 限流 | 按账号 + 接口 | 按设备 + 用户 + 接口 |
| 接口风格 | 支持批量、导出 | 单动作、强幂等 |
| 审计 | 全量操作审计 | 关键行为审计 |
| 返回体 | 含管理端展示字段 | 裁剪敏感字段 |

### 11.5 视图对象隔离

11.5.1 同一领域对象应分别定义 B 端与 C 端的响应对象，命名体现端别（如 `Admin*` / `App*`）。

11.5.2 C 端响应不得包含内部标识、成本、库存明细、操作人等字段。

11.5.3 实体到视图对象的转换在接口层完成，服务间 DTO 不得直接作为对外响应。

### 11.6 内部调用安全

11.6.1 内部服务间调用应携带服务令牌（3.13），网关与下游同时校验。

11.6.2 下游服务不得无条件信任来自任意来源的身份头（M-10），应校验来源为网关或持有有效服务令牌，防止内网越权。

11.6.3 身份、租户与语言等信息经 `ServiceHeaders` 约定头透传、由公共上下文读取传递，业务代码不得直接解析请求头。

## 12. 数据规范

### 12.1 数据归属与访问边界

12.1.1 每个服务独占其数据库（或独立 schema），不得跨服务共享表（M-03），保证数据可独立演进。

12.1.2 禁止跨库 JOIN（M-04）；跨服务数据获取应通过接口或订阅变更事件构建本地读模型（3.9）。

12.1.3 服务不得直接访问其他服务的数据库账号。

12.1.4 服务拆分未定稿时，不得提前建立跨库视图或共享表以「临时过渡」；此类临时方案会固化为长期耦合。

### 12.2 冗余与读模型

12.2.1 数据冗余仅允许在读模型场景使用，且必须明确同步机制与一致性容忍窗口。

12.2.2 读模型的重建应支持全量回放，回放过程不得影响线上主链路。

### 12.3 标识、缓存与变更管理

12.3.1 主键生成应使用全局唯一方案（雪花 / 号段），不得依赖数据库自增作为跨服务标识。

12.3.2 缓存键应带服务前缀，避免多服务共享缓存时的键冲突。

12.3.3 数据库变更应通过版本化迁移脚本管理，不得手工改表；迁移工具全工程统一为 Flyway（脚本随代码同仓、按版本顺序执行），生产环境 `ddl-auto` 取 `validate`，schema 以迁移脚本为唯一来源，Hibernate 不负责建表。

### 12.4 多租户

12.4.1 租户隔离（租户字段注入与过滤）应由 framework 数据访问增强（8.2.1）统一实现，业务代码不得绕过或手写租户条件。

12.4.2 跨租户数据访问仅限平台管理场景，需显式声明并纳入审计。

## 13. 服务通信

### 13.1 通信方式选型

13.1.1 通信方式按下表选型：

| 方式 | 适用场景 |
|---|---|
| 同步调用 | 需即时结果的查询与命令 |
| 异步消息 | 事件通知、最终一致、削峰 |
| 事件驱动 | 跨域状态同步 |

### 13.2 调用与消息约束

13.2.1 单个用户请求的同步调用链不得超过 3 个服务（M-07，含网关与 BFF，按同步调用深度计）；超限时应改为异步编排或聚合服务，避免延迟放大与故障传导。

13.2.2 异步消息应携带 traceId（3.11）、幂等键与版本号；每个消费主题必须配置死信（3.12）通道。

13.2.3 事件定义归发布方所有，消费方不得反向修改事件。

13.2.4 消息应按业务域设置主题，消费组命名与服务名对应。

13.2.5 服务间调用关系应以依赖图形式维护，新增或变更调用关系时同步更新。

## 14. 可观测性与运维

### 14.1 日志与链路

14.1.1 日志：统一结构化输出，必含 `traceId`、`service`、`spanId`；业务日志不得打印敏感信息。

14.1.2 链路：HTTP、服务调用、消息三通道均需透传 traceId；采样率按环境配置。

### 14.2 指标与健康检查

14.2.1 指标：每个服务应暴露 Rate、Error、Duration 指标与 JVM、连接池指标。

14.2.2 健康检查：应提供存活与就绪探针，就绪探针需校验关键依赖可用性。

### 14.3 配置与密钥

14.3.1 配置集中于配置中心，按命名空间隔离环境；本地仅保留启动级配置。

14.3.2 配置变更应支持灰度生效与回滚。

14.3.3 密钥、凭证与敏感配置应由密钥管理服务或部署环境注入，不得入库、不得硬编码、不得提交至代码仓库；轮换后应及时失效旧凭证。

### 14.4 告警

14.4.1 核心接口错误率、P99 延迟、消息积压、线程池与连接池饱和度应有阈值告警。

## 15. 部署与交付

### 15.1 镜像与容器

15.1.1 每个服务实现模块应包含独立 Dockerfile，产出独立镜像。

15.1.2 镜像标签应与服务版本一致，不得使用 `latest` 部署到生产（M-13），保证版本可追溯。

15.1.3 容器编排应配置资源 requests/limits、副本数、弹性伸缩指标与优雅停机。

### 15.2 发布策略

15.2.1 B 端与平台服务宜采用滚动发布；C 端核心服务宜采用灰度（3.10，网关权重 + 请求头路由）。

### 15.3 CI 流水线

15.3.1 CI 应包含以下阶段：

| 阶段 | 内容 | 失败影响 |
|---|---|---|
| validate | 依赖规则（17.1）、代码规范（17.2）、契约校验 | 阻断 |
| compile | 变更模块及其上游编译 | 阻断 |
| test | 单元、契约、集成测试（16.1） | 阻断 |
| package | 服务镜像构建 | 阻断 |
| deploy-dev | 开发环境部署与冒烟 | 阻断 |
| deploy-prod | 灰度 → 全量 | 阻断并触发回滚 |

### 15.4 回滚

15.4.1 回滚应支持按服务维度独立回滚，不得要求整站回滚。

15.4.2 回滚演练应纳入发布验证，确保发布单内记录的回滚路径真实可用。

## 16. 测试规范

### 16.1 测试分层

| 类型 | 范围 | 要求 |
|---|---|---|
| 单元测试 | 领域层、应用层、工具类 | 核心逻辑覆盖率 ≥ 70% |
| 切片测试 | 接口层、数据访问、服务调用客户端 | 关键接口必备 |
| 契约测试 | 所有对外暴露的 `*-api` | 提供方与消费方双向校验 |
| 集成测试 | 服务内完整链路 | 事务、幂等、多租户场景必备 |
| 端到端测试 | 网关 → 服务 → 消息 主流程 | 核心流程覆盖 |
| 故障注入 | 下游超时、消息堆积、依赖不可用 | 核心服务宜覆盖 |

### 16.2 测试环境约束

16.2.1 集成测试不得依赖开发者本地环境或共享测试库。

16.2.2 跨服务流程测试应使用契约桩或独立测试环境，不得在生产数据上验证。

## 18. 服务生命周期管理

### 18.1 新增服务

18.1.1 新增服务应按以下流程执行：

1. 提交服务拆分方案：限界上下文、数据所有权、依赖关系、调用链、部署单元。
2. 通过架构评审后，在 `acme-cloud` 下创建服务目录，含契约模块与实现模块。
3. 在对应子聚合器的 `<modules>` 中登记，并在 `acme-cloud` 的 `dependencyManagement` 中登记本项目模块版本。
4. 实现契约模块（DTO、枚举、服务调用接口），并补充契约测试；按 17.1 为 `*-api` 配置禁用 Web / ORM 依赖的 enforcer（9.1.2）。
5. 实现服务模块，按 10.1 的分层职责组织代码。
6. 在网关注册路由与鉴权策略（见 11.1.3）。
7. 配置独立的数据库 schema、配置中心条目与消息主题。
8. 接入 trace、日志、指标与健康检查（第 14 章）。
9. 编写 Dockerfile 与部署清单，配置资源与探针。
10. 更新服务清单文件与依赖图（5.3.3、13.2.5）。
11. 补充单元、契约、集成测试（16.1），并验证限流、降级与回滚。

### 18.2 服务合并与下线

18.2.1 服务合并前应完成消费方迁移；合并操作遵循 5.3.2，历史契约保留一个版本周期（见 9.3.1）。

18.2.2 服务下线应按以下顺序执行：

1. 确认无消费方：核对依赖图，并结合网关访问日志与 MQ 消费统计验证；
2. 摘除网关路由，冻结该服务发布；
3. 进入观察期（≥ 1 个完整业务周期），确认无流量、无消息积压；
4. 停止实例并释放计算资源；
5. 归档数据、配置与迁移脚本；
6. 更新服务清单文件与依赖图（5.3.3、13.2.5）。

18.2.3 下线服务的契约模块应保留至所有消费方升级完成，再从 `dependencyManagement` 移除。

18.2.4 消息主题不得随服务下线立即删除，应保留至确认无消费方后按消息治理策略废弃。

## 19. 例外与豁免

19.1 本规范中「不得」条款的例外必须经架构评审批准，不得以口头决定或临时变通方式绕过。

19.2 豁免申请应记录：规则编号、业务原因、影响范围、补偿措施、有效期。

19.3 豁免有效期不得超过一个版本周期或 6 个月（取较短）；到期前应复查，逾期自动失效。

19.4 豁免清单应与服务清单（5.3.3）同仓维护，作为审计与复查依据。
